## 1. 目标与范围

将图模板实例化升级为条件驱动、可重放、可审核的执行引擎；将患者状态更新与路径执行关联；实现随访风险处置真实闭环。暂不开发 MWM 推理、生成式 MDT、AI 自动随访、通用工作流平台。不重写前端、不引入微服务或 Docker 强依赖。

## 3. T20 路径执行内核

现状：generate_plan_tasks 将全部非 START/END 节点生成任务，未选择条件边。
拟在 services 下新增 graph_execution.py，保留 plans.py 作为计划编排入口。图契约扩展 edge_id、condition(rule_id/version/expected_result)、gateway_type、join_policy；迁移旧无条件边为显式无条件。发布校验引用、可达性、互斥分支、默认分支、汇合及环。首期只支持 DAG，循环复评使用显式新事件或新计划，拒绝未支持图类型。
执行：
1. 从 START 遍历可达节点；条件边使用同一冻结规则上下文。
2. XOR 网关仅允许一个确定匹配；多个匹配为配置错误，未知且可能改变选择则等待补充，不默认选 FALSE。无匹配且无显式默认边则阻断。
3. AND 网关展开明确的并行边；汇合仅等待本次已激活的前驱，不等待未选择分支。首期不支持隐式 OR 汇合。
4. 生成选中任务与依赖；未选分支不生成可执行任务，但记录决策轨迹；未知网关生成待补充事件，禁止其下游执行。
5. 保存 execution_trace（快照、规则版本、边、结果、原因、时间）；计划审批绑定图哈希与轨迹哈希。运行中遇到新条件，走 T22，不静默改变审批结果。
验收：TRUE/FALSE/UNKNOWN、互斥冲突、并行汇合、无匹配、非法环、未选分支不执行；同输入重放结果一致（忽略随机 ID 与生成时间）。

## 4. T21/T23 患者状态与规则

现状：activate_plan 使用 plan.snapshot_id；build_context 可能混合历史快照与其他观测；部分缺失布尔字段通过 is True 的反向判断可能被当作阴性。
建立统一 RuleContext：patient_id、snapshot_id、as_of、observation_refs、ruleset_version、数据质量与来源。仅使用时点内、属于该患者且经校验的观测；不允许未来数据泄漏。区分未测、未知、阴性、过期、单位不兼容。规则目录由服务端注册，禁止客户端任意声明有效版本。
激活前在事务中检查最新有效快照、关键观测更新、规则版本与审批指纹；有关键变化或过期则返回 409 PLAN_REASSESSMENT_REQUIRED，生成待重评事项；禁止覆盖旧审批。按专家配置字段有效期，不擅自设定临床阈值。激活与观测更新竞争通过患者状态版本或锁协调。
三值真值表：NOT UNKNOWN=UNKNOWN；AND 有 FALSE 则 FALSE，否则有 UNKNOWN 则 UNKNOWN；OR 有 TRUE 则 TRUE，否则有 UNKNOWN 则 UNKNOWN。排除及安全条件未知须阻断；未知规则、版本不匹配、单位错误不得通过。逐条审查 RULE-001/002/003/004/005/008/009/010 的缺失值语义。
验收：历史与最新快照冲突、未来观测、缺失转移/腹水、明确阴性、单位错误、规则未知、关键观测更新与激活并发均有测试。

## 5. T22 动态重评与重规划

临床事件导入或人工确认后生成状态变化事件，按规则依赖索引找到受影响实例；产生重评建议或变异，不自动改变治疗。轻量数据库事件表/Outbox 即可。
旧计划 ACTIVE → 新计划 DRAFT → 审核 → 原子切换；新旧任务通过稳定 node_key 与执行语义匹配，保留历史完成记录及证据，未完成任务标记迁移/取消原因；不能仅复制完成状态而丢失来源。新任务依赖重新映射，旧计划任务不可继续执行。临床安全阻断时冻结受影响任务并提示人工处置。
验收：重复事件幂等、已完成任务保留、拒绝新计划不替换旧计划、旧任务不可执行、并发激活最多一个 ACTIVE、重规划后依赖有效。

## 6. T24 随访风险闭环

现状：escalate_followup 同时填写 notified_at 与 acknowledged_at，未实际通知或签收；close 可直接填写 resolved_at；未确认抽取可写入结构化记录。
拟新增 FollowupAlert、FollowupContact 独立记录（迁移旧 JSON 保留来源），状态 OPEN → NOTIFICATION_PENDING → NOTIFIED → ACKNOWLEDGED → IN_ACTION → RESOLVED → CLOSED；通知失败可重试，不能伪造送达。站内队列可作为首期渠道，明确区分入队、送达、阅读、签收。签收须由授权责任人操作，处置需记录结果，关闭须验证已处置。独立保存原话、待确认抽取、确认人和确认时间；未确认信息不得作为正式临床观测。
拟新增 POST /followup-alerts/{id}/acknowledge、/resolve、/close；通知适配器未配置返回明确状态。校验治疗事件归属、责任人、同意状态及联系权限；风险排序使用明确等级映射。危险信号规则由专家审阅，未配置时仅人工升级，不声称自动分诊。紧急情况提示及时就医，不等待系统处理。
验收：通知失败、重复升级、未签收关闭、跨科室签收、未确认抽取、拒绝随访、并发联系记录均有负向测试。

## 7. T25 并发与审计

任务更新使用 UPDATE WHERE id AND row_version AND expected_status，检查影响行数，失败返回 409；同事务检查计划状态和依赖，必要时锁定实例或使用版本条件。计划版本、入径幂等键、事件导入键、每实例唯一生效计划建立数据库约束（SQLite/PostgreSQL 分别验证）。避免仅用 len(plans)+1 分配版本。
成功业务变更与审计同事务提交；拒绝审计独立事务；外部通知使用事务性 outbox、幂等消费、重试与失败记录。审计不存病历正文、密码或令牌。迁移前备份，验证升级及恢复。
验收：两个独立数据库会话竞争同一任务/计划，只有一个成功；模拟审计写失败业务回滚；重复事件不重复生成任务；SQLite 文件库及 PostgreSQL 集成测试分别执行，后者为生产前门槛。

## 8. T26/T27 前端

保留现有 UI。逐页核查路径设计器、审批、患者路径/地图/回放、变异、随访、知识、模拟、分析、驾驶舱及设置。支持真实 API 的页面完成查询、写入、错误、加载、空态及缓存失效；尚无真实 API 的功能在 Server 模式明确禁用或标注不可用，不展示 mock 业务结果。路径画布保存须真实持久化，校验使用后端结果。
使用显式 VITE_DATA_MODE=demo/server（拟议名称，实施时与现有配置统一）；Server 模式登录失败不得调用本地 loginAs，身份以 /me 为准，401 清理会话及患者缓存；403 不回退。Demo 数据和真实数据命名空间隔离，退出清理缓存。令牌存储方案在生产安全设计中复核。
验收：断网、503、401、403、刷新、切换账号、跨科室、模拟模式隔离；后端写入后各相关页面一致。
